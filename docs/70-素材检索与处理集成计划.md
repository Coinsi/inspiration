制定日期：2026-10-04；本机本轮验收收尾：2026-10-05（北京时间）。本文同时记录实施计划、实测结果与未验证边界，不代表所有模型、格式和负载均已通过。

## 目标

将 WISE 的多模态检索与 MediaCMS 的媒体入库、预览、转码和字幕能力实际集成到 inspiration 素材模块。用户继续在现有素材页上传、查看处理进度、搜索、预览片段并引用到创作，不需要分别管理三个系统。

固定上游版本与服务边界；复用现有素材 ID、不可变版本、权限和引用关系，建立外部服务映射；打通上传、原片保留、预览、转码、转写任务；接入文字、图片、画面、声音及可选人脸物体检索并返回时间段；补齐增量索引、删除同步、失败恢复、取消和资源限流；统一素材页面、处理进度、片段预览与创作引用；用真实素材验证及长视频批量压力测试。

不扩展到自动成片。性能结论必须有对应规模的实测，研究级或尚未验证的功能不能标为完成。现有检索/转写实现保留用于兼容，但不能用它们的测试代替 WISE/MediaCMS 真实集成证据。

尊重用户主目录预览偏好：以 `C:/Code/Python/inspiration` 的当前工作区为实施位置；修改前核对主目录与工作树差异，保留全部现有未提交更改。本轮不因历史授权自动提交、合并或推送。

## 数据与服务边界

1. inspiration 是素材、不可变版本、存储对象、项目授权和创作引用的唯一业务来源；上传和生成入库走相同入口。
2. 处理任务以 `素材版本 + 处理器 + 配置/模型版本` 为幂等基础，保存外部 ID、阶段、重试次数、错误、心跳、取消请求和产物映射。
3. MediaCMS 仅负责媒体处理。私有媒体下载和转写需要桥接 API，不能把外部内部 URL 直接发给浏览器绕过项目权限。
4. WISE 负责特征和检索索引。查询经过 inspiration 授权，命中需要映射回素材版本、起止时间、命中模态与证据；不允许跨项目结果泄露。
5. 原片不可变；分析副本保持时间映射。索引模型或参数更换创建新版本，保留旧快照并在完整性校验后原子发布。当前重建与查询串行，重建期间查询暂不可用，返回503忙碌状态，页面提示稍后重试；旧索引并行在线查询仍是后续目标。
6. 删除先执行现有引用保护和逻辑删除，再投递外部清理。任何失败可重试；恢复与清理并发需要代际/版本约束，不能清掉恢复后的对象。

## 上游固定与现实限制

版本记录位于 `deploy/media-services/upstream-lock.json`。MediaCMS 固定 `v9.1.0 / 1ab99af4587bfc515582783c9ee19ae12e0fd065`；WISE 固定 `fcfa443fbb46eb361bb19151339338616838a5b5`（包版本 `2.1.0+dev`，GitHub 无 release）。应用源代码 pin 不覆盖基础镜像/系统依赖/模型，部署后仍须保存镜像 digest 和模型 revision/checksum。

- MediaCMS 默认上传会将原片复制到它自己的本地媒体目录；当前集成在派生文件回存 CAS 后清理临时副本，处理峰值仍包含副本、转码与临时文件。失败/未完成任务可能保留副本，必须受队列和容量预算约束。零拷贝、共享对象存储需要专门扩展，不能仅靠挂卷或写配置就视为实现。
- WISE 的默认入库、建索引、在线服务是不同步骤；增量/删除/恢复闭环需要桥接和任务编排。
- 默认抽帧会漏掉短促动作；命中的候选范围不等于最佳剪辑点。音频语义、字幕全文和画面检索需要分别评测。
- 上游字幕支持与自动 ASR 入库不是同一个状态；必须实际生成字幕并保存时间段后才标为可搜索。
- 物体、人脸会增加推理、存储和许可要求，按需开启。InsightFace 默认权重有非商业研究限制，不随 WISE Apache 许可自动获得商用权。
- 多模态续作已扩展产品本地上传入口：视频、静态JPEG/PNG/WebP图片、WAV/MP3/FLAC/M4A/OGG音频。图片64MiB以内并校验真实解码与像素，图片无时长；音频校验真实音轨并生成浏览器可播预览。各类型的上传、处理、检索、引用分开验收，不能仅因桥接接受文件就视为完整产品流程通过。
- 首版 MediaCMS 桥接按完整视频流式转码，保存任务阶段并不等于编码分片/帧级断点续跑；HLS 和视频雪碧图暂不导入，专用集成路径关闭相应重处理，保留 poster、MP4 preview 与 360p/720p 文件。
- 50 个一小时 50 Mbps 原片约 1.125 TB；单片处理中的原片副本另需约 22.5 GB，转码和临时文件额外计算。若把全量同时复制且未清理，原片层面可达 2.25 TB，因此不能无界批量预传。当前机器当时剩余约 1034 GiB，原片总量本身已超过可用空间，不足以直接执行这一全量样本。
- 业务素材上传默认单文件 **10 GiB**（`library_max_upload_bytes`），而转送层默认 50 GiB、MediaCMS 上限 100 GiB、WISE 分析输入上限 8 GiB；这些是不同层的限制。上述 22.5 GB 一小时原片目前会先被业务入口拒绝。开放小时 4K 必须连同上传断点、空间预约、配额和恢复验证一起调整，不能只调大 sidecar 限制。

## 资源与运行策略

上传与处理分离；短作业与长作业需要调度，初始重处理并发为 1，设置每步超时、临时空间配额、最小剩余空间、重试上限和取消检查。按阶段持久化，重启后恢复任务，禁止全片全部帧一次装入内存。

素材状态应能区分：文件已保存、等待处理、预览可用、字幕可搜、画面可搜、声音可搜、部分失败。上游未部署/模型未安装的状态应显示不可用，不伪装为成功或无限等待。

开发环境核查：Docker 29.5.2、Compose v5.1.4，Docker Linux engine 由用户启动后可达；RTX 4060 Laptop 8 GiB，主机约 63 GiB 内存。首版 CPU 容器可验证集成，不足以证明 GPU 吞吐或长视频并发能力。

Docker Linux VM 当时可用内存上限约 31 GiB，不能把宿主 63 GiB 全部当作容器预算。多套服务的上限总和、系统缓存与实际峰值必须一起考虑。
