# 工程功能覆盖与验收

日期：2026 年 10 月 18 日。依据 [工程设计](README.md)、[操作契约](CONTRACTS.md) 与当前代码基线 `d7ba587`。

## 验证结论与边界

下列 48 个使用场景逐项列出了目标定位、数据表达、修改路径和失败处理。第二轮校验后共有 64 项设计探针通过，验证了选定的结构规则和小型算法；场景推演不等于完整 schema 或算法证明。发现的问题、修订和仍未关闭的设计事项见 [设计校验报告](DESIGN_REVIEW.md)。

这不是 48 项功能上线报告。样例没有真实媒体，也没有实现渲染、跟踪、图像编辑、分轨、动态歌词或多机事务。数据结构能承载这些内容，不证明工具能生成满意作品，也不证明性能达到生产要求。

本轮实际命令，工作目录为仓库根目录：

```powershell
python -m unittest discover -s docs/architecture/editable-project -p "verify*.py" -v
```

结果：64 tests，OK。T01 至 T30 在 `verify_design.py`，T31 至 T64 在 `verify_contract_edges.py`。不依赖外部服务，不调用收费模型，不修改线上数据库。

## 代表场景的完整推演

### 两处复用只修改一处

初始：sequence@1 的 first 与 second 分别指向 fight-a@1 与 fight-b@1，两者都引用 sword-comp@1，后者引用 glow@1。

请求：仅第一处剑光强度从 0.7 改为 0.3。

变化：创建 glow@2、sword-comp@2、fight-a@2、sequence@2，只更新 first 路径。second 仍指向 fight-b@1 及 sword-comp@1。没有复制原视频，也没有改 glow@1。

机器证据：T14 同时检查旧对象不变、两条引用路径分别采用正确修订，且原输入包未被函数修改。正式版本还要验证真实渲染和多个输出根联合更新。

### 音量调整与换配音

“对白太小”先定位 voice-use；如果独立音轨存在，可调实例增益并保存新工程修订，不生成新源音频。如果只有混合音轨，需要分离或重新配音能力，不能直接承诺单独调整人声。

“换成更紧张的配音”产生新音频候选。原对白文本、人物和保护要求作为生成输入。候选长度改变时字幕、口型、片段结束和后续布局进入检查；原子变更可一起更新，也可以保留候选等待决定。

机器证据：T21 验证旧对白长度前提拒绝字幕提交；T23 验证跨对象校验失败不改变原状态。这些不是数据库事务测试。

### 动态歌词

样例将歌词合成放在主时间线 3 秒处。主音乐从源 1 秒开始，因此歌词局部 0 秒对应音乐源 4 秒，避免只保存一句“跟随音乐”却没有映射。

正式歌词载荷需支持 cue、word 或 grapheme 级稳定 ID 和对齐范围；中文逐字动画不能只依赖空格分词。动画曲线与当前对齐版本绑定。修改第二句只更新其内容或时间，但重排、字体和相邻避让可能扩大实际渲染影响。

机器证据：样例表达依赖，T15 检查字体更新影响歌词及海报而不影响剑光。逐字对齐、动画和实际视觉结果未执行。

### 剑光与遮挡

源视频生成轨迹和身体遮挡蒙版，轨迹驱动拖尾，再施加发光；合成以原视频为背景并按遮挡蒙版组合。身体遮挡需要在正确空间和时间里求值，不能只把视频与一张静态图片叠加。

跟踪变化使拖尾、发光、合成和两处使用重新检查。字体变化不影响剑光。拖尾需要前面一段帧，故局部修改不能假设只重渲染当前帧。

机器证据：T03、T04、T34 检查非法端口和环；T16 检查引用升级的潜在对象影响；T49 至 T51 检查单时间坐标的失效范围公式。跨文档范围求解、蒙版正确性和渲染尚未验证。

### 眼神与武器的生成式修改

请求记录图像或视频版本、人物区域、参考用途、保留要求和修改范围。新结果是候选资源并带来源；不能在原图上覆盖。用户保留面部和构图的要求需要观察和人工判断验证。

视频场景还需要动态区域和一致性检查。原始视频没有人物图层时，工程不得假装已有可直接编辑的眼睛或武器属性。跟踪、抠像、重绘或重生成是实际工具能力，必须分别接入。

本轮为结构推演。需要用真实媒体检查区域外变化、人物身份与帧间一致性；当前无通过证据。

### 打斗方案重做

先绑定场景、涉及镜头与用户反馈。方案 A 只改变剪辑、反应镜头和音效；方案 B 补充动作及新镜头。各自形成候选分支，共享已有资源，保留不可修改镜头。

比较时需要场景级预览而不是单镜头评分。采用方案 B 的一部分声音到方案 A，形成新的组合候选，重新检查时长、动作卡点和空间连续性。不能将“更精彩”自动等同于更快、更多特效或分数更高。

本轮为结构推演。动作设计、补镜工具、质量评估和用户审阅界面未实现验证。

### 用户转向与并行修改

运行 A 基于旧工程制作特效，用户已经采用另一个镜头。A 完成后发布可追溯结果并创建候选；采用前检查使用位置当前版本，失败则保留候选，不写新选用状态。

运行 B 改封面且没有读取受影响镜头，可以在新 HEAD 上重放自己的命令。必须保留用户的新镜头选择，不能用旧快照覆盖。数据库事务与分支 CAS 仍需真实并发测试。

机器证据：T22、T24、T25，覆盖简化的前提检查与保留无关新状态。

## 设计审查中修正的缺口

| 初始设计容易遗漏的点 | 本版修正 | 剩余实施风险 |
| --- | --- | --- |
| 只保存图层和时间线 | 加入带类型计算输入、辅助数据和独立音频结构 | 执行器选择与实际性能 |
| 改共享合成影响所有地方 | 固定引用与单路径写时复制 | 多根、多路径的真实提交算法 |
| 字段不相同就自动合并 | 读取前提、布局和语义不变量 | 服务端依赖提取是否完整 |
| 毫秒能够涵盖所有编辑 | 有理数时间、媒体采样基准和映射 | VFR、倒放、音频重采样实现 |
| 局部效果只重算当前帧 | 窗口、整段、有状态依赖与保守失效 | 缓存范围编译准确性 |
| 任务完成即替换当前结果 | 候选发布与采用分离 | 供应商超时、恢复和费用对账 |
| 素材全局标记最终版 | 采用决定绑定具体使用位置和版本 | 旧 selected 状态的迁移 |
| 未知插件可以忽略后导出 | 原样保留并阻止相关正式执行 | 旧客户端与迁移行为 |
| 一个完整包含所有历史 | 明确输出闭包和导出配置 | 保留策略、授权与大文件迁移 |

## 实施顺序与放行条件

0.3 已将时间/同步、编辑命令、媒体类型、多对象采用、迁移与运行存续的规则细化到 [工程细化契约](DETAILED_CONTRACTS.md)，新增 T65–T105 的适用边界见 [校验记录](DESIGN_REVIEW_03.md)。下表的真实执行放行条件仍未通过，不因设计探针增加而自动完成。

| 阶段 | 交付 | 必须通过 |
| --- | --- | --- |
| A 工程内核 | 修订、固定引用、目标地址、精确时间、变更与预检 | 真数据库原子性、并发、幂等、权限、旧结果保护 |
| B 旧能力迁移 | 现有素材、剪辑、音轨、字幕、视觉层的读取与写入适配 | 固定数据迁移前后时间、画面和声音对照；可回退 |
| C 原生合成 | 图层、蒙版、文字、关键帧、基础效果与一致渲染语义 | 动态歌词、基础叠加、音量自动化实际样片 |
| D 专业处理 | 跟踪、局部修图、声音分离、口型、复杂效果 | 分能力验证质量、失效范围、费用与失败恢复 |
| E Agent 制作 | 按需工具目录、上下文和候选修改闭环 | 从用户指导到局部修改与确认采用的完整流程 |

阶段 A 和 B 可先利用当前模块化后端，不需要先搭建庞大分布式基础设施。C 的渲染技术选型要在 A 的接口冻结前完成小范围可行性验证，以免定下无法一致执行的效果语义；验证结果可以修订草案，不能当作用户要求已经实现全部特效。

## 尚不能给出的保证

- “打斗更精彩”“眼神正确”等创作质量，无法靠工程格式保证。
- 任意三维、第三方效果或未来模型能力，不能仅凭扩展字段声称可执行。
- 浏览器与服务端逐像素一致、随机生成复现、长片性能和数百任务并发，均需真实执行证据。
- 任意专业软件格式的无损往返、字体和插件可分发性，需要具体格式与依赖条件核查。

设计的目标是让这些能力有明确接入位置、修改规则和验收标准。没有通过的能力不会因为数据能够保存而被报告为可用。
