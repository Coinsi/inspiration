# 新业务能力怎样接入 Harness

更新：2026-10-23。本文说明当前可用的扩展接口和仍需开发的连接点，不承诺“任意新工具注册一下就能完成全部生命周期”。

## 1. 已经解耦的边界

领域服务和工具执行器应接受项目、用户、作品、固定输入与业务请求标识，返回可检查的领域结果。它们不应依赖某个文字模型的会话、SDK、提示词或私有内存。共享入口为：

- `tools.registry.register(Tool(...), handler, review_handler=None)`：名称、说明、Pydantic schema、版本、分组和领域 handler。handler 签名为 `(db, ctx, context, parsed)`。
- `tools.capabilities.register_contract(name, ToolPolicy(...))`：权限、作用范围、副作用、幂等、取消、恢复、是否启动任务、是否计费、输出类型和 JSON schema。
- `harness.plan_contracts.register_preflight(name, validator)`：可选的纯校验函数 `(db, ctx, context, parsed)`。不得调用正式 handler、提交付费请求、创建候选或改变用户数据。
- `tools.invocation.invoke(...)`：统一检查当前成员权限、范围、能力和版本，验证输入/输出并返回 `ToolResult`。独立 HTTP/CLI/后台消费者也能调用；调用者仍负责事务边界、持久化回执和恢复策略。

具体实现在 [registry.py](../../../backend/app/modules/tools/registry.py)、[capabilities.py](../../../backend/app/modules/tools/capabilities.py)、[invocation.py](../../../backend/app/modules/tools/invocation.py) 和 [plan_contracts.py](../../../backend/app/modules/harness/plan_contracts.py)。新工具不必改文字模型的内核实现。

当前工具注册仍由应用启动代码显式导入/调用，不是任意第三方包自动发现、热安装或无审查执行插件。新增权限名称必须先进入应用权限表；已有角色和租户边界不能因为注册工具而扩大。

## 2. 按结果类型决定接入工作量

| 新能力类型 | 可复用的部分 | 仍必须实现/连接的部分 |
| --- | --- | --- |
| 同步读取、检索、计算建议 | registry + contract + 可选 preflight；按需发现、冻结版本、统一调用和普通观察回执 | 真正的数据读取、权限/固定引用校验、有限返回；声明 read 的 handler 必须没有副作用 |
| 同步创建工程候选 | 上述接口；可调用现有工程命令/候选服务，保持读前提和写范围 | 领域校验、稳定业务键、候选文件/文档及预览方式；新候选类型需接结果验证/审阅，不能仅返回 `candidate_id` |
| 直接采用/删除/发布 | 独立用户审阅与领域权限机制 | Agent 调用层禁止 `adopt` 自动执行；不能把采用伪装为 read/candidate 或让普通模型回执充当批准 |
| 返回已有媒体结果 | 固定 Generation/Blob 引用、技术验收与父任务成果聚合 | 必须证明结果归属当前任务/明确依赖；任意 URL/文本不能作为已交付媒体 |
| 长时间本地计算或远端生成 | 既有任务持久化、租约、outbox、上下文与资源框架可以借鉴 | 实际启动、等待、进度、恢复、取消、计量、结果校验的专用桥接；仅设置 `starts_job=True` 不会自动补齐 |
| 新工程效果/文档类型 | 工程固定修订、候选审阅、CAS 和来源记录 | 同步增加 schema、执行器、能力声明、预览/技术验证、读写冲突规则、归档/迁移策略；只有 JSON 字段不算支持 |

普通同步工具通常不需要修改 runtime 的动作协议。**全新候选、媒体产物或长期任务类型不是零改动接入。** 当前 `verification.py` 识别的工程候选种类是明确列举的；`starts_job` 当前主要影响调用事务方式，runtime 的等待分派仍对已接入工具/任务类型显式处理。

## 3. 同步工具的落地步骤

1. 在独立业务模块实现服务。数据库写入、素材处理和权限不能放进模型提示词；不可让模型提供凭据、执行租约或伪造系统请求键。
2. 定义严格 schema（通常 `extra='forbid'`），写清单位、数量上限、固定 ID/修订/哈希、错误类别；列出不支持的操作。涉及编辑时选择现有工程命令能表达的最小变更。
3. 注册工具与 `ToolPolicy`。将当前实际能力写进描述，不列出未实现算法。`output_kind` 是分类信息，不能代替真实输出验证。
4. 需要访问源/校验配方时注册只读 preflight；不把正式 `compose`/生成 handler 用作“试运行”。深层执行校验仍需在写入/派发前进行。
5. 在应用启动中注册模块，并把必要的有限工具集合加入适用的规划/发现路径。任务 grant 只允许继承或缩小；“可发现”不是“可调用所有工具”。
6. 通过 `invoke` 做独立领域测试，再通过真实 harness 任务测试。复用 `test_harness_tools.py` 的无内核调用、跨项目拒绝、输出不合法回滚、固定技能与审阅案例。

工具版本、输入/输出 schema、权限或副作用发生变化，已有计划的冻结契约会拒绝继续执行。升级必须重新验证或明确迁移，不要保留相同版本却改变含义；也不要绕过漂移检查让旧任务静默使用新行为。

## 4. 长任务必须补齐的生命周期

参考现有 [job_wait.py](../../../backend/app/modules/harness/job_wait.py)、[transcription_wait.py](../../../backend/app/modules/harness/transcription_wait.py)、[recovery_tools.py](../../../backend/app/modules/harness/recovery_tools.py) 和 [validation_stage.py](../../../backend/app/modules/harness/validation_stage.py)。新类型至少需要以下具体连接：

1. **提交前**：持久化稳定请求、固定源、原配置、权限来源、输出硬限和费用/资源预留；事务/投递恢复不能重复计费。模型不能自行扩大授权。
2. **已受理后**：保存领域任务 ID 和上游句柄，再执行昂贵工作；派发提交成功而本地回执丢失时能找回原任务。查询接口不能偷偷重新提交。
3. **等待桥接**：把工具回执转换成持久等待状态，并加入 `claim` 的只读对账。返回一个 `job_id` 本身不会自动让任意新工具进入等待。
4. **恢复桥接**：依靠原业务键/句柄找到唯一任务；匹配不到或匹配多项时保留不确定，不能自动猜测重发。资源预留也必须重新关联同一任务，避免结果恢复而额度永远不结算。
5. **控制桥接**：暂停阻止新派发，已受理结果可保存；取消和新的指导要隔离迟到写入。能否停止远端计算要准确声明。
6. **结果桥接**：固定媒体或领域候选落库，真实技术/领域验证，结算已测量用量，唤醒明确依赖。只有通过验证才推进到可交付终态。
7. **人工边界**：候选审阅、采用与原运行互通；批准指向固定候选和指纹。用户已手改或基线已变化时重新验证，不回写旧结果。
8. **故障测试**：提交前崩溃、提交后丢回执、下载失败、权限撤销、源漂移、暂停/取消与成功竞态、两任务共用上限、物理文件损坏、重复恢复都要跑。

新 harness `media.generate` 已复用 `engineering/delivery.py` 的持久投递表和后台循环，但明确区分 `local_replay` 与 `remote_receipt`。前者可以重新计算，后者只在尚未领取时重投同一 Job；工作进程失联后，已知句柄要显式重新接收，未知提交维持不确定并保留费用预留。旧工作进程的阶段写入、产物发布和上游取消也必须受租约约束。新增适配器不能仅套用本地重算策略，尤其不能因队列重投而重发已受理的付费请求。

目前尚无统一的可注册 JobBridge 接口来自动覆盖上述专用等待器。需要新增长期任务类型时，应明确评估 runtime/service 中的分派连接点；不要宣传工具核与生命周期已经完全插件化，也不要为了减少代码而省略费用/恢复/终态验证。

## 5. 不应透传给用户的复杂度

用户在一个创作对话里提供目标、参考、指导和确认。能力目录、工具发现、执行参数、等待句柄属于系统。必要时只向用户展示缺失能力、需要选择的目标、费用范围或无法安全恢复的原因。

例如新增配音工具后，用户仍可说“这段台词换成低沉一些的声音”；系统需把它定位到固定音频/角色/片段，保留旧版本、生成候选、重新检查时长和字幕同步。注册一个 `speech.generate` 名称并不能代替这些领域规则。
