# Inspiration 云端扩缩容方案

设计稿，基于 2026 年 11 月 20 日主分支 `194840d`。下文的节点模板、迁移流程和性能门槛是实施目标。

目标是让更多人能同时登录、浏览素材、播放、对话、编辑和导出，并维持可接受的响应时间与成功率。用户少时，一台主机可以兼跑应用和媒体处理。增长时，运维分别调整应用、预览和导出等节点组的实例数量，每个新增的健康节点自动接流量或领任务。用户从原地址打开项目，能继续编辑、续传和查看先前提交的任务。日常扩容、应用发版与数据库迁移各自独立执行。

## 单机起步时怎样扩容

第一版建议直接使用云平台伸缩组的“期望实例数”作为运维入口。首台主机固定运行，额外的应用节点和处理节点分组管理，各组初始都是 0。节点模板、私网服务地址、权限和健康检查提前配好，新增机器可以沿用当前发布的镜像与现有数据。

例如首台已运行一个导出进程。导出积压时，把“额外导出节点”从 0 调到 2，系统应自动启动两台机器，合计三台能处理导出。重复设置为 2 应维持同一目标数量。网页访问增长时，对“额外应用节点”做同样的操作。运维能看见目标数、就绪数，以及新节点接到的请求或任务。新节点启动失败时保留原节点服务，给出失败原因。

高峰过后，把额外节点数调回 0。新增节点先退出流量入口或停止领单，处理完在途工作后再回收。单机阶段可以用两个隔离的进程或容器、各自的临时目录检查节点启动和排空。跨主机访问、云配额和实际开机时间留给放量前的一次真实节点演练，验收结束后可回到单机。

## 业务流量增长时，加什么

| 用户正在做的事 | 先看什么 | 如何增加容量 |
| --- | --- | --- |
| 登录、打开项目、查找素材、保存剪辑 | 各入口每秒请求数、成功率、P95 延迟、数据库连接等待 | 应用繁忙时增加实例。数据库饱和时先处理连接和慢查询，给鉴权、项目读取和保存预留资源。 |
| 和 Agent 同时对话或恢复会话 | 活跃连接、重连次数、首段回复等待时间、进度查询造成的数据库负载、模型供应商限流 | 按瓶颈处理应用长连接、进度读取或供应商配额。模型调用按项目限制并发，已提交任务可回查。 |
| 上传素材与附件 | 活跃上传数、每秒写入字节、分片失败率、暂存和长期存储用量 | 授权浏览器分片直传共享存储。临时盘吃紧的节点暂停接大任务，已确认的分片可续传。 |
| 同时播放、拖动进度条 | 首帧等待、卡顿率、热点与首次访问文件的源站带宽 | 通过授权读取和 CDN 给播放流量独立的出口。热门内容由缓存节点提供，首次访问也要验证源站承载力。 |
| 请求预览、索引或导出 | 各队列最老等待时间、到达与完成速度、存储读写吞吐 | 分组增加处理机。优先处理用户正在等待的预览，历史索引和批量转码可延后。 |

沿用 FastAPI、PostgreSQL、Redis/Celery 和已有对象存储接口。共享数据库保存作品版本、权限、上传会话、任务和进度，队列负责分发。Agent 工作空间按用户和项目授权，关联作品时也保存作品与版本。任务接手者用同一组授权和持久化进度继续工作。内容哈希用于定位和去重，读取素材仍须校验项目权限。

## 流量突增前要准备什么

**先取得整站基线。** 记录日常高峰时上述操作各占多少、用到多大的素材，以及用户实际等多久。上线新活动或扩大用户范围前，按预期同时在线人数和操作组合确定目标峰值，写下核心操作的响应时间、成功率和可接受排队时间。每次演练留下已测容量、开始变慢的环节和对应的扩容动作。

**把扩容入口提前跑通。** 用真实节点验证镜像、权限、私网连通、负载均衡注册以及领取第一份任务。记录从负载上升、监控发出告警到新容量实际可用的总耗时。事先核对云主机配额、数据库连接、媒体带宽、模型供应商额度和费用上限，保留可手动调高节点数的入口。可预见的峰值提前开机，平时根据实测补位时间留出余量。

**覆盖新机器启动期间的空档。** 给登录、打开项目和保存作品留出应用与数据库容量，让已授权的播放继续由媒体出口承载。可以等待的工作进入有容量上限的持久队列。接近上限时先放缓历史索引等后台任务，再对新提交的重任务按项目限流，向用户显示排队或稍后重试。已接收的任务可按原任务 ID 查询，重复点击也只登记一次。[Google SRE 过载处理](https://sre.google/sre-book/handling-overload/)

**扩容后确认体验恢复。** 在高峰流量仍持续时，检查核心操作是否达标、任务完成速度是否超过新任务到达速度、最老等待是否逐步回落。等积压消化、流量回落后再缩容。若机器已加而等待仍在增长，按上表检查数据库、存储、入口带宽与上游额度。[队列积压与恢复](https://aws.amazon.com/builders-library/avoiding-insurmountable-queue-backlogs/)

## 实施顺序与交付物

| 阶段 | 要交付的改动 | 进入下一阶段的条件 |
| --- | --- | --- |
| 1．保护当前单机 | 分开上传与封面的锁，保留上传容量预留。采集整站混合负载基线，按项目限制重任务并发，并显示排队进度。 | 批量处理视频期间，其他用户能登录、浏览、播放和保存。记录首个瓶颈、核心操作延迟和错误率。 |
| 2．让文件跨机器可用 | 优先采用同地域的托管对象存储。落地分片直传、授权读取和旧对象迁移。盘点素材库、聊天附件、工程包导入导出、预览与生成结果的本机目录。 | 换 API 节点仍能续传，换处理节点仍能读取原片。老作品、历史版本、工程包在新存储上均可打开。 |
| 3．让后台任务可以接手 | 将媒体处理从 API 启动流程迁出，分开短预览、重渲染、Agent 与外部模型任务。按任务原子领取，领取事务提交后执行耗时工作。执行者定时续期，持久保存步骤结果。 | 两台机器能分别领取两份任务。停止其中一台后，另一台能接手，作品只登记一条有效结果。 |
| 4．把加减机器变成一次操作 | 提供应用节点、处理节点两种模板，以及健康检查、负载均衡和缩容前排空。发布流程单独执行一次数据库迁移。先手动调实例数，压测达标后再启用自动扩缩。 | 先用两台独立主机验证跨机正确性，再按预计高峰逐档增加实例，记录每一档的吞吐、交互延迟和缩容结果。 |

第一条跨机链路选“上传一个视频 → 生成预览 → 剪辑导出 → 从原作品打开成片”。它同时经过存储、网页请求、后台任务和作品写回。先用这条链路验证节点模板，再将附件、工程包和 Agent 长任务纳入同一套换机验证。低流量阶段可短期开第二台做演练。

## 素材存储与容量

生产环境优先选与应用同云、同地域的私有托管对象存储。应用、Agent 和渲染节点共用一个存储入口，按权限读写。素材从 100 GB 增到 1 TB 时，继续写入同一存储空间，作品引用和应用机器都能沿用。以阿里云 OSS 为例，单个桶没有预设容量上限，存储量、读写请求和公网下行流量分别计费。上线前对所选服务实测分片续传、短期签名、按字节范围播放和处理机内网读取。[容量规则](https://help.aliyun.com/zh/oss/user-guide/oss-bucket-overview) · [计费组成](https://help.aliyun.com/zh/oss/billing/)

如果以后要求素材全部放在自有机器上，可以沿用相同的素材引用和读写接口，将对象迁入独立的分布式存储集群。以分布式 MinIO 为例，容量通过新增存储池扩展。采用这条路线需要提前规划盘组、数据冗余和恢复，并验证现有单机数据的迁移。[MinIO 存储池扩容](https://www.min.io/blog/add-pools-expand-capacity)

| 素材或文件 | 保存在哪里 | 何时可以释放空间 |
| --- | --- | --- |
| 原始视频、图片、音频，作品采用的生成结果，保留的历史版本或成片 | 私有对象存储。数据库记录素材版本、内容哈希和物理位置。作品按版本引用，同一原片可以有多种剪法。 | 按作品、历史版本、附件和运行中任务的引用核对。解除最后一个引用、经过保留期并再次检查后，才可回收原件。 |
| 封面、缩略图、可播放的低码率视频 | 保存在共享存储，获准访问同一原片的作品和处理节点可复用已有预览。 | 原片可读且能重新生成时，可以按使用频率淘汰。某份预览若被用户保存为独立素材，它的持久引用仍保护该内容。 |
| 上传中的分片和未发送的附件草稿 | 新上传的分片由对象存储保管，会话和归属保存在数据库。已发送或已收入素材库的附件遵循相应保留规则。 | 用户取消或会话过期时释放对应分片。活跃上传可继续，未发送的草稿沿用草稿过期规则。[附件规则](../../backend/app/modules/attachments/cleanup.py) |
| 渲染解码、合成时产生的临时文件 | 当前处理机的临时盘，接单前检查剩余空间。需要跨机接手的步骤结果先写共享存储并登记。 | 任务完成、取消或临时文件可安全重建时，释放本机工作目录。 |

**一份原片，多处使用。** 一段 2 GB 的同字节视频被三个作品采用，按现有去重机制，正常情况下共用一份 2 GB 的原片。三个作品各自记录选取的素材版本、入出点与效果。重新编码后的文件、单独生成的预览、备份会额外占空间。项目成员通过素材记录取得读取授权，知道文件哈希也不能替代授权。素材列表按数据库中的项目和文件夹分页，已入库文件可以先选用，语义索引可随后补齐。[内容去重](../../backend/app/storage/cas.py) · [原片和预览记录](../../backend/app/models/library.py) · [素材目录](../../backend/app/modules/library/service.py)

**清理与成本。** 管理端分别观察去重后的原件体积、可重建副本、未完成分片、备份和公网下行流量。只对确认可丢弃的临时对象设置自动到期。原件回收沿用已有的标记、宽限期、复查引用和按确切物理位置删除机制。接入多个存储端后，删除记录还要标明存储端，避免误删迁移后的新副本。改用直链时，读授权的最长有效期也要纳入回收宽限期。[引用核查](../../backend/app/storage/retention.py) · [现有回收流程](../../backend/app/storage/garbage_collection.py)

## 历史素材和传到一半的视频怎么迁

1. **先让兼容版本读懂两个存储位置。** 为对象位置标明存储端、桶和完整对象键，保留原有素材、版本 ID 和内容哈希。已有工具处理本地文件到 MinIO，跨两个对象存储端的迁移还要补上。[已有迁移工具](../../backend/app/maintenance.py)
2. **先切一小批新上传。** 持久保存归属、上传 ID、分片号、已确认分片及预期大小。服务端授权后由浏览器直传，重连时核对已完成分片，最终校验大小与完整内容哈希，再登记可见版本。重复完成请求应返回同一版本。[分片续传机制](https://docs.aws.amazon.com/AmazonS3/latest/userguide/mpuoverview.html)
3. **让旧会话能传完。** 切换时，已开启的上传会话继续路由到持有暂存文件的原节点。确需提前下线时，先暂停该会话追加，搬运已传字节并核对偏移，再切换续传位置。旧节点保留到在途会话全部有去向。
4. **后台复制旧文件，逐份核验再切读。** 记录迁移进度，对照大小和完整内容哈希，成功一份再更新一份位置。验证覆盖历史作品、附件和正式成片。回退时保留能读两端的应用版本，使新端独有文件继续可读。旧副本清理放在观察期、备份恢复演练和引用核对之后。

## 新机器如何加入、退出和接手

**加入。** 运维调整节点组目标数量。模板从统一发布记录读取镜像版本，按角色领取配置和凭据。将生产 Compose 中固定的数据库、Redis 容器地址改为可配置的私网服务地址。应用节点通过就绪检查后加入流量入口，处理节点确认能读写共享存储后开始领单。每组设置数据库连接预算，为交互请求保留连接。

**首台主机的保护。** 将首台主机排除在可回收的伸缩组之外。若数据库或队列暂留在这台主机，它的故障仍会影响全站。进入有连续可用要求的阶段，再为数据库、队列配置故障切换，并演练数据库、对象和必要密钥的配套恢复。

**有序退出。** 先把应用节点从入口摘除，给现有请求收尾时间。处理节点先停止领新任务，再完成手头任务或保存可接手进度。随后回收机器及临时盘。原片和用户保留的版本继续占用对象存储，过期分片和可重建预览可按保留策略回收。

**意外中断。** 数据库保存任务状态、素材版本、当前执行者和租约期限。派发遗漏时由扫描器重新投递，重复消息按任务 ID 合并。另一台机器从已保存的步骤继续，没留下检查点的转码可以从该步重跑。结果先写对象存储，再凭有效租约和作品版本条件登记，晚到的旧节点不能覆盖较新的编辑。已经提交给模型厂商的任务用原上游任务 ID 查询。提交结果未知时先对账，避免一次视频生成被重复计费。[现有上游提交状态处理](../../backend/app/modules/generation/model_routing.py)

## 从两台扩到更多机器

扩容的操作单位是一个节点组。例如网页访问平稳、导出在排队时，可以让应用组维持两台，把导出组从两台调到四台、八台或更多。负载均衡器根据健康状态维护应用节点名单，每台渲染机从指定队列领取任务，领取和结果提交都按任务 ID 协调。作品、用户和任务不需要人工分配到主机。项目并发配额和上游模型限额由各节点共同遵守，增加机器不会放大同一用户或同一密钥的额度。

每次升档前先核对共享资源余量。仓库中的生产配置将 PostgreSQL 的总连接数设为 60。应按各组实例数、每实例进程数、每进程连接池上限计算最坏占用，另外计入发布时同时存活的新旧进程、后台调度和管理预留。若连接预算不足，先调整连接池或数据库容量。媒体处理还要观察队列派发速度、对象存储的读写吞吐和内网带宽，区分处理机在编码和在等待输入的时间。[生产数据库配置](../../deploy/production/compose.yml) · [PostgreSQL 连接设置](https://www.postgresql.org/docs/current/runtime-config-connection.html)

缩容时先按当前排队量和允许等待时间确定要保留的就绪处理能力，再分批停止其余节点领单。固定的数据节点不参与回收。运维记录最近一次达标的节点数、机器规格和任务组合，作为下一次放量的容量依据。

## 放量前的验收

先在预发布使用独立主机、各自的临时盘和同一组共享服务验证正确性。容量演练按预计业务峰值逐档增加真实计算资源。下表的容量档位按该角色已就绪的机器总数计算，包括承担该角色的首台主机。机器数和性能数字是首轮建议，实际可承载的并发量由压测填写。

| 演练 | 通过条件 |
| --- | --- |
| 从单机调高额外节点数，操作中不登录新机器，再调回 0 | 只改组的期望数量，就能看到新节点接到真实请求或任务。重复设置同一数量不会额外开机。缩回 0 后首台和共享数据保留，作品可打开、在途任务有结果或可接手。 |
| 用户甲导出多个视频，用户乙同时剪辑 | 乙能打开、修改、保存并重新打开作品。混合负载下保存请求的 P95 建议在 1 秒内。两个用户的项目权限始终生效。 |
| 保持日常操作组合，短时间内从日常流量跃升到预计峰值，持续到新节点就绪并消化积压 | 同时回放登录、浏览与保存、上传、播放、对话和导出。记录告警、接入新容量和恢复的时刻。新节点启动期间验证核心操作的成功率与延迟，计入向真实用户返回的繁忙或限流结果。扩容后队列等待回落，已接收的上传和导出均可找回。 |
| 新增应用节点，将同一会话的请求分给 A、B | B 能读到 A 刚保存的作品，并能接回对话进度。两个节点同时修改同一旧版本时，用户得到版本冲突提示，新内容不被静默覆盖。 |
| 在 A 开始大视频上传，断线后经 B 继续 | 浏览器只补缺少的分片。最终文件哈希与原件一致，重复完成请求后素材库仍只有一个对应版本。 |
| 同一原片被多个作品引用，其中一个作品移除素材 | 其他作品和保留的历史版本仍能播放、重新导出。无授权的账号无法取得读取链接。清除可重建的预览后，系统能从原片生成新的预览。 |
| 导出积压时从一台加到两台 | 从调整实例数到新节点接第一单，首轮目标为 10 分钟内，包含开机和镜像拉取。在相同规格和素材组合下，建议双机每分钟完成的本地转码数至少为单机的 1.5 倍，同时记录作品保存延迟。 |
| 分别把应用组和导出组按 1 → 2 → 4 → 8 台升档，按实际需求继续测试 | 每次只改变一个组。应用组测保存 P95 达标时可承载的请求量。导出组固定素材与编码组合，保持有足够的独立任务可领，测每分钟完成量。再按预计高峰同时施加两类负载，测排队时间和保存 P95。继续加机而吞吐趋平时，定位共享瓶颈，调整后重测。 |
| 正常缩容一次，再模拟处理节点意外退出 | 排队任务有去向，运行中的任务有结果或可恢复状态。作品只登记一条有效成片，已确认的上游生成复用原任务，提交状态未知的进入核对。 |
| 在已有积压时分批从八台缩到四台，另做多台同时失联的演练 | 健康节点继续领取新任务。排空中的节点完成或交还手头任务，意外失联节点的任务在租约到期后按原有规则接手。检查每份任务的最终状态和唯一有效结果，并记录积压恢复所需时间。 |
| 单节点临时盘接近预留线，并另行演练存储切换及回退 | 吃紧节点暂停领大任务，其他健康节点仍能工作。切换前后的作品都能打开，新增素材和在途上传能找回，恢复出来的数据库引用能定位到实际文件。 |

记录机器规格、媒体大小与时长、并发浏览与上传数、队列等待、保存 P95、单位时间完成量，以及数据库连接和媒体带宽。待基线稳定，再按交互延迟扩应用，按每台处理机的待处理工作量和可接受等待时间扩处理节点，设置预算上限与缩容冷却时间。[按队列负载扩缩的参考](https://docs.aws.amazon.com/autoscaling/ec2/userguide/as-using-sqs-queue.html)
